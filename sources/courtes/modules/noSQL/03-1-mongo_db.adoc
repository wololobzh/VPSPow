== Les avantages principaux de MongoDB

MongoDB est un SGBD orienté document offrant plusieurs avantages majeurs :

* Haute performance en lecture
* Haute disponibilité
* Mise à l'échelle automatique
* Stockage orienté documents (JSON-like)

[NOTE.speaker]
--
 MongoDB est conçu pour des applications nécessitant rapidité, flexibilité et scalabilité. Sa nature orientée document permet de stocker des données complexes dans des formats proches du JSON. Il s'adapte très bien à des contextes de forte croissance ou d'évolution rapide du modèle de données.
--

== BSON : le format interne de MongoDB

MongoDB utilise le format **BSON**, une représentation binaire optimisée du JSON, plus rapide à analyser et adaptée aux types avancés.

Exemple simplifié :

```
{"hello": "world"} →
\x16\x00\x00\x00 // total document size
\x02              // type String
hello\x00         // field name
\x06\x00\x00\x00world\x00
\x00              // end of object
```

[NOTE.speaker]
--
 BSON permet d'encoder efficacement les données avec des types supplémentaires (Date, BinData, ObjectId, etc.). Cela améliore les performances et réduit l'encombrement des données.
--

== Flexibilité du schéma et ACID

MongoDB offre :

* Un schéma **optionnel**, permettant une forte flexibilité
* Le **sharding** pour le scaling horizontal
* Le support des propriétés **ACID** (transactions multi-documents depuis la version 4)

[NOTE.speaker]
--
 La flexibilité du schéma permet à une collection de contenir des documents de formes différentes. Cela est très pratique dans des systèmes évolutifs. Le support ACID assure la fiabilité dans des opérations critiques.
--

== La réplication dans MongoDB

La réplication sert à synchroniser les données sur plusieurs serveurs.
Elle permet :

* La redondance
* Une disponibilité accrue
* Une meilleure tolérance aux pannes

[NOTE.speaker]
--
 MongoDB utilise des **Replica Sets**. En cas de défaillance du primaire, un secondaire prend automatiquement le relais. Cela garantit la continuité de service.
--

== Réplication et performances

La réplication peut également :

* Améliorer la vitesse de lecture
* Améliorer la disponibilité dans des environnements géodistribués
* Fournir des copies supplémentaires pour reporting, audit ou sauvegarde

[NOTE.speaker]
--
 Les nœuds secondaires peuvent être utilisés pour répartir la charge sans pénaliser le nœud principal. Cela améliore l'efficacité des lectures à grande échelle.
--

== Le Sharding dans MongoDB

Le sharding permet de distribuer des données sur plusieurs serveurs afin de :

* Gérer des volumes trop importants pour une seule machine
* Répartir la charge
* Augmenter la capacité globale du cluster

[NOTE.speaker]
--
 Le sharding s'effectue au niveau des collections. MongoDB décompose les données en "chunks" répartis sur plusieurs shards. Le tout est orchestré par le routeur `mongos` et les serveurs de configuration.
--

== Sharded Cluster

Un cluster shardé contient :

* Des shards
* Des serveurs de configuration
* Des routeurs `mongos`

[NOTE.speaker]
--
 Le routeur `mongos` s'occupe de rediriger les requêtes vers les bons shards. Cela permet au client d'accéder aux données sans connaître leur emplacement.
--

== Une autre façon de penser les relations

MongoDB ne supporte pas nativement les relations clé primaire / clé étrangère.

Dans MongoDB, on peut :

* **imbriquer** des documents (subdocuments)
* **référencer** des documents via leur `ObjectId`

[NOTE.speaker]
-- 
 L'imbrication améliore fortement les performances en rassemblant dans un seul document les informations connexes. Les références existent mais sont plus coûteuses, car elles nécessitent plusieurs requêtes.
--

== Normalisation vs Dénormalisation

**Normalisation** : éviter les redondances. Recommandé principalement pour les relations *one-to-many*.

**Dénormalisation** : réplication volontaire de données. Utile pour les relations *many-to-many* ou les modèles hiérarchiques.

[NOTE.speaker]
--
 MongoDB privilégie la dénormalisation : elle limite les besoins de jointures, améliore la lecture et permet d’organiser les données selon l’usage réel de l'application.
--

== Modèle de données hiérarchique

MongoDB permet de représenter des structures hiérarchiques via des documents imbriqués.

[NOTE.speaker]
--
 Ce modèle permet des lectures rapides mais peut entraîner des documents volumineux, ce qui peut ralentir certaines opérations.
--

== Limitations de la normalisation

Normaliser excessivement dans MongoDB peut poser problème, en particulier dans un environnement shardé.

[NOTE.speaker]
--
Les opérations de type JOIN sont limitées et parfois impossibles si les documents concernés sont répartis sur plusieurs shards. Cela peut nécessiter de compenser via du code applicatif.
--
// end::deroulement[]

== Conclusion
// tag::conclusion[]
* MongoDB est performant, scalable et flexible grâce à son modèle documentaire.
* BSON permet un stockage efficace et adapté aux types avancés.
* La réplication et le sharding garantissent disponibilité et mise à l'échelle.
* La normalisation ou la dénormalisation dépend des contraintes du modèle et de l'usage.
// end::conclusion[]
