== Introduction aux tests unitaires

* Les tests unitaires vérifient le bon fonctionnement de petites unités de code isolées
* Ils constituent la base d'une stratégie de tests efficace
* Avantages des tests unitaires :
  ** Détection précoce des bugs
  ** Documentation vivante du code
  ** Facilitation des refactorisations
  ** Amélioration de la qualité du code

[NOTE.speaker]
====
Les tests unitaires sont la forme la plus élémentaire de tests automatisés. Ils permettent de s'assurer que chaque partie du code fonctionne correctement de manière isolée.

Insister sur le fait que les tests sont un investissement qui fait gagner du temps à long terme, même s'ils semblent chronophages au début.

Mentionner que dans le développement moderne, les tests unitaires sont considérés comme une bonne pratique incontournable, particulièrement dans les équipes.
====

== Présentation de Vitest

* Framework de test moderne pour JavaScript/TypeScript
* Développé par l'équipe de Vite (même écosystème que Svelte)
* Avantages de Vitest :
  ** Rapide et optimisé pour Vite
  ** Compatible avec l'API de Jest (facile à apprendre)
  ** Support natif de TypeScript et ESM
  ** Hot Module Replacement (HMR) pour les tests

[NOTE.speaker]
====
Vitest est particulièrement bien adapté aux projets Svelte car il s'intègre parfaitement dans l'écosystème Vite.

Expliquer que Vitest est plus rapide que Jest pour les projets basés sur Vite, car il réutilise la configuration Vite et évite les transformations inutiles.

Si certains étudiants connaissent déjà Jest, les rassurer en expliquant que la syntaxe est très similaire et que la transition est facile.
====

== Configuration de Vitest dans un projet Svelte

=== Installation des dépendances

```bash
npm install -D vitest @testing-library/svelte jsdom
```

* `vitest` : le framework de test
* `@testing-library/svelte` : utilitaires pour tester les composants Svelte
* `jsdom` : émulation du DOM pour les tests

[NOTE.speaker]
====
Expliquer que jsdom est nécessaire pour simuler un environnement de navigateur lors des tests de composants.

Testing Library suit la philosophie de tester le comportement plutôt que l'implémentation, ce qui rend les tests plus robustes face aux refactorisations.
====

=== Configuration de Vitest

Créer ou modifier le fichier `vite.config.js` :

```javascript
import { defineConfig } from 'vite';
import { svelte } from '@sveltejs/vite-plugin-svelte';

export default defineConfig({
  plugins: [svelte()],
  test: {
    globals: true,
    environment: 'jsdom',
    setupFiles: ['./src/setupTests.js']
  }
});
```

[NOTE.speaker]
====
Expliquer chaque option de configuration :

- `globals: true` permet d'utiliser les fonctions de test (describe, it, expect) sans les importer
- `environment: 'jsdom'` configure l'environnement pour simuler un navigateur
- `setupFiles` permet de spécifier des fichiers à exécuter avant les tests

Mentionner qu'il faudra créer le fichier setupTests.js dans le dossier src.
====

=== Fichier de configuration des tests

Créer le fichier `src/setupTests.js` :

```javascript
import '@testing-library/jest-dom';

// Configuration globale pour les tests
```

[NOTE.speaker]
====
Ce fichier permet d'étendre les assertions disponibles avec des matchers spécifiques au DOM, comme `toBeInTheDocument()`, `toHaveTextContent()`, etc.

On peut aussi y ajouter des mocks globaux ou des configurations spécifiques pour tous les tests.
====

=== Configuration du script npm

Ajouter dans `package.json` :

```json
"scripts": {
  "test": "vitest run",
  "test:watch": "vitest",
  "test:coverage": "vitest run --coverage"
}
```

[NOTE.speaker]
====
Expliquer la différence entre les commandes :

- `test` exécute les tests une seule fois
- `test:watch` exécute les tests en mode watch (relance les tests à chaque modification)
- `test:coverage` génère un rapport de couverture de code

Montrer comment lancer les tests avec `npm test`.
====

== Structure d'un test unitaire

=== Anatomie d'un test Vitest

```javascript
// src/utils/math.js
export function sum(a, b) {
  return a + b;
}

// src/utils/math.test.js
import { describe, it, expect } from 'vitest';
import { sum } from './math';

describe('sum function', () => {
  it('adds two numbers correctly', () => {
    expect(sum(1, 2)).toBe(3);
  });
  
  it('handles negative numbers', () => {
    expect(sum(-1, -2)).toBe(-3);
  });
});
```

* `describe` : groupe de tests liés
* `it` ou `test` : cas de test individuel
* `expect` : assertion qui vérifie un résultat

[NOTE.speaker]
====
Expliquer que `describe` est utilisé pour regrouper des tests liés, ce qui améliore la lisibilité des rapports de test.

`it` et `test` sont synonymes, on peut utiliser celui qu'on préfère.

Les assertions avec `expect` sont le cœur des tests, elles vérifient que le code se comporte comme prévu.

Montrer quelques matchers courants : toBe, toEqual, toBeTruthy, toContain, etc.
====

=== Cycle de vie des tests

```javascript
import { beforeEach, afterEach, beforeAll, afterAll } from 'vitest';

describe('test group', () => {
  beforeAll(() => {
    // Exécuté une fois avant tous les tests
  });
  
  beforeEach(() => {
    // Exécuté avant chaque test
  });
  
  afterEach(() => {
    // Exécuté après chaque test
  });
  
  afterAll(() => {
    // Exécuté une fois après tous les tests
  });
  
  it('test case', () => {
    // Test
  });
});
```

[NOTE.speaker]
====
Les hooks de cycle de vie sont très utiles pour :

- Préparer l'état initial avant les tests
- Nettoyer après les tests pour éviter les effets de bord
- Partager du code de configuration entre plusieurs tests

Donner des exemples concrets : initialisation d'une base de données en mémoire, création d'instances de composants, etc.
====

== Démonstration

**Écriture de tests unitaires simples**

[NOTE.speaker]
====
1. Créer un fichier `src/utils/string-utils.js` avec quelques fonctions utilitaires :
+
```javascript
export function capitalize(str) {
  if (!str) return '';
  return str.charAt(0).toUpperCase() + str.slice(1).toLowerCase();
}

export function reverse(str) {
  return str.split('').reverse().join('');
}
```

2. Créer un fichier de test `src/utils/string-utils.test.js` :
+
```javascript
import { describe, it, expect } from 'vitest';
import { capitalize, reverse } from './string-utils';

describe('String utilities', () => {
  describe('capitalize function', () => {
    it('capitalizes the first letter of a string', () => {
      expect(capitalize('hello')).toBe('Hello');
    });
    
    it('lowercases the rest of the string', () => {
      expect(capitalize('HELLO')).toBe('Hello');
    });
    
    it('handles empty strings', () => {
      expect(capitalize('')).toBe('');
    });
  });
  
  describe('reverse function', () => {
    it('reverses a string', () => {
      expect(reverse('hello')).toBe('olleh');
    });
    
    it('handles palindromes', () => {
      expect(reverse('radar')).toBe('radar');
    });
  });
});
```

3. Exécuter les tests avec `npm test` et montrer les résultats
4. Introduire intentionnellement un bug dans une fonction et montrer comment le test échoue
5. Corriger le bug et montrer que les tests passent à nouveau

== Bonnes pratiques et astuces

=== Organisation des tests

* Structure des fichiers de test :
  ** Placer les tests à côté des fichiers qu'ils testent
  ** Nommer les fichiers avec `.test.js` ou `.spec.js`
* Grouper les tests logiquement avec `describe`
* Nommer les tests de manière descriptive

[NOTE.speaker]
====
Insister sur l'importance de bien nommer les tests. Un bon nom de test sert de documentation et aide à comprendre ce qui ne va pas quand le test échoue.

Recommander d'utiliser la convention "Given-When-Then" ou "Arrange-Act-Assert" pour structurer les tests.

Expliquer que les tests doivent être indépendants les uns des autres pour éviter les effets de bord.
====
