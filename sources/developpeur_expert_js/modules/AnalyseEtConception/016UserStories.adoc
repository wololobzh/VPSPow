[NOTE.speaker]
====
Les *user stories* (histoires utilisateur) sont des descriptions simples et concises des besoins et attentes d’un utilisateur. Elles servent de base pour guider le développement de fonctionnalités dans les projets agiles, en tenant compte du point de vue utilisateur.

Les user stories ne font pas partie d’UML, mais elles peuvent jouer un rôle clé dans la phase d’analyse qui précède la création des diagrammes UML.
====

== Qu'est-ce qu'une User Story ?

Une *user story* est une phrase courte qui décrit une fonctionnalité du point de vue de l'utilisateur. Elle se concentre sur le *pourquoi* et le *pour qui* de la fonctionnalité, plutôt que sur le *comment*. 

Les *user stories* sont un outil essentiel en méthodologie agile, car elles aident les équipes à rester centrées sur les besoins réels de l'utilisateur final.

[NOTE.speaker]
====
Les *user stories* permettent de formuler les fonctionnalités en gardant à l’esprit l’objectif utilisateur, ce qui aide à développer des produits répondant mieux aux attentes. Cette approche centrée utilisateur garantit que chaque tâche de développement apporte une valeur réelle.
====

== Structure d'une User Story

La plupart des *user stories* suivent un modèle simple pour être claires et concises :

*En tant que* [type d'utilisateur], *je veux* [action/fonctionnalité] *afin de* [bénéfice].

Voici un exemple de *user story* :

*En tant que* visiteur du site, *je veux* m'inscrire à une newsletter, *afin de* recevoir les dernières actualités et offres.

Dans ce modèle :

* **En tant que** : spécifie qui est l'utilisateur et sa perspective.
* **Je veux** : décrit l'action ou fonctionnalité demandée.
* **Afin de** : clarifie l’objectif ou le bénéfice de la fonctionnalité.

[NOTE.speaker]
====
Ce modèle est essentiel car il aide à structurer les besoins de manière compréhensible pour toutes les parties prenantes du projet. En précisant l’objectif utilisateur, il devient plus facile pour l’équipe de se focaliser sur l’impact de la fonctionnalité, et non simplement sur son développement technique.
====

== Les Critères d'une Bonne User Story : INVEST

Une bonne *user story* doit respecter le modèle **INVEST** :

== Les Critères d'une Bonne User Story : INVEST

- **I - Indépendante** : Une *user story* doit être autonome pour éviter les dépendances.

== Les Critères d'une Bonne User Story : INVEST

- **N - Négociable** : Elle ne doit pas être une spécification figée, mais une base de discussion.

== Les Critères d'une Bonne User Story : INVEST

- **V - Valuable ** : Elle doit apporter une valeur concrète pour l'utilisateur.

== Les Critères d'une Bonne User Story : INVEST

- **E - Estimable** : L’équipe doit pouvoir estimer le temps et les ressources nécessaires pour la réaliser.

== Les Critères d'une Bonne User Story : INVEST

- **S - Small ** : Elle doit être suffisamment concise pour être complétée en un sprint.

== Les Critères d'une Bonne User Story : INVEST

- **T - Testable** : Elle doit pouvoir être validée par des tests clairs, ce qui garantit qu'elle est complète.

== Les Critères d'une Bonne User Story : INVEST

Le modèle **INVEST** est une référence utile pour évaluer la qualité d’une *user story*.   

[NOTE.speaker]
====
Le modèle **INVEST** est une référence utile pour évaluer la qualité d’une *user story*. Une *user story* trop large ou non testable est difficile à prioriser et risque de ne pas être réalisée correctement. Nous allons nous entraîner à vérifier chaque *user story* avec ce modèle pour nous assurer qu’elle respecte les critères.
====

== Exemples et Pratiques de User Stories

Voici quelques exemples de *user stories* bien rédigées, suivies d'une analyse en fonction des critères INVEST.

== Exemples et Pratiques de User Stories

1: *En tant que* client inscrit, *je veux* consulter mon historique de commandes, *afin de* retrouver mes achats passés et faciliter mes réclamations :

   * **Indépendante** : Peut être réalisée seule, sans attendre d'autres fonctionnalités.
   * **Négociable** : Des discussions peuvent se faire pour déterminer l’affichage des commandes.
   * **Valuable** : Aide l’utilisateur à gérer ses commandes et à améliorer l’expérience client.
   * **Estimable** : Les développeurs peuvent estimer le temps nécessaire pour créer cette fonctionnalité.
   * **Small** : Peut être réalisée dans un sprint de développement.
   * **Testable** : Peut être vérifiée en accédant à un historique de commandes fonctionnel.

[NOTE.speaker]
====
Chaque *user story* doit répondre aux besoins utilisateur et pouvoir être réalisée de manière autonome. Cet exemple montre comment appliquer INVEST pour évaluer la qualité d’une *user story*. Les apprenants vont maintenant s'exercer en créant leurs propres *user stories* et en les testant avec INVEST.
====

== Exemples et Pratiques de User Stories

2: *En tant que* visiteur du site, *je veux* utiliser une barre de recherche, *afin de* trouver facilement les produits qui m’intéressent :

   * **Indépendante** : La barre de recherche peut être développée indépendamment d'autres fonctionnalités.
   * **Valuable** : Aide l’utilisateur à naviguer efficacement dans le site.
   * **Estimable et testable** : Facilement estimable et testable avec des recherches simples.

[NOTE.speaker]
====
Chaque *user story* doit répondre aux besoins utilisateur et pouvoir être réalisée de manière autonome. Cet exemple montre comment appliquer INVEST pour évaluer la qualité d’une *user story*. Les apprenants vont maintenant s'exercer en créant leurs propres *user stories* et en les testant avec INVEST.
====

== Exercice Pratique : Création de User Stories

// tag::exercice[]
*Objectif de l'exercice* : Créer des *user stories* en respectant la structure et en appliquant les critères INVEST.

=== Enoncé

Vous travaillez sur un projet de développement d’une application de gestion de tâches personnelles. L'application doit inclure des fonctionnalités pour organiser, planifier et suivre des tâches. Voici les besoins de votre utilisateur cible :

1. **Ajout de tâches** : Les utilisateurs veulent ajouter de nouvelles tâches à leur liste.
2. **Organisation par priorité** : Les utilisateurs veulent organiser leurs tâches par priorité (haute, moyenne, basse).
3. **Suivi des tâches terminées** : Les utilisateurs veulent pouvoir marquer les tâches comme terminées.

Pour chaque besoin, rédigez une *user story* en respectant la structure : *En tant que* [type d'utilisateur], *je veux* [action/fonctionnalité] *afin de* [bénéfice].

[NOTE.speaker]
====
Cet exercice pratique permet d’appliquer directement les concepts abordés. En formulant les *user stories* de manière claire et structurée, les apprenants apprendront à rester centrés sur l’utilisateur et à anticiper les questions ou besoins potentiels de l’équipe de développement.
====

=== Travail attendu

Pour chaque besoin identifié, rédigez une *user story* en :

* Utilisant le modèle *En tant que… je veux… afin de…*
* Vérifiant qu’elle respecte les critères INVEST.

=== Exemples de correction possible

1. **Ajout de tâches**  
   *En tant que* utilisateur de l'application, *je veux* ajouter une nouvelle tâche à ma liste, *afin de* garder une trace de mes tâches à réaliser.*

2. **Organisation par priorité**  
   *En tant que* utilisateur de l'application, *je veux* pouvoir classer mes tâches par priorité, *afin de* me concentrer d'abord sur les tâches les plus importantes.*

3. **Suivi des tâches terminées**  
   *En tant que* utilisateur de l'application, *je veux* marquer les tâches comme terminées, *afin de* voir facilement ce qui reste à faire.*

[NOTE.speaker]
====
Ces exemples de correction montrent des *user stories* bien structurées et orientées vers l’utilisateur. Elles sont concises et respectent le modèle INVEST, garantissant ainsi qu’elles sont compréhensibles et réalisables.
====
