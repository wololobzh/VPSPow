== Introduction au problème N+1 et à DataLoader

Lorsqu'une requête GraphQL récupère des données imbriquées, elle peut déclencher des requêtes redondantes, ce qu'on appelle le problème **N+1**. Par exemple, si une requête nécessite des données pour chaque élément dans une liste, une requête initiale est envoyée pour tous les éléments (1 requête), suivie de requêtes supplémentaires pour chaque élément (N requêtes), ce qui devient inefficace pour des ensembles de données de grande taille.

**Solution :** DataLoader permet de regrouper les requêtes identiques et de les mettre en cache. Il regroupe les requêtes similaires en une seule et stocke les résultats pour éviter les appels redondants dans la même requête.

[NOTE.speaker]
====
Le problème N+1 peut être résolu en regroupant et en mettant en cache les requêtes pour optimiser l'accès aux données, ce qui réduit la charge sur la base de données.
====

== Étape 1 : Installation de DataLoader

Installez le package `dataloader` pour utiliser les fonctionnalités de regroupement et de mise en cache des requêtes.

[source,bash]
----
npm install dataloader
----

[NOTE.speaker]
====
Le package `dataloader` est spécialement conçu pour regrouper et mémoriser en cache les requêtes dans une API GraphQL, permettant d’optimiser les appels vers des sources de données externes.
====

== Étape 2 : Utilisation de DataLoader dans la source de données

Nous allons implémenter DataLoader dans une classe source de données `PersonDataSource`, en l’utilisant pour optimiser la méthode `getPerson`.

1. Importez DataLoader et configurez un **loader** pour regrouper les requêtes dans `PersonDataSource`.

[source,typescript]
----
// src/datasources/PersonDataSource.ts

import DataLoader from 'dataloader';

export class PersonDataSource {
  private loaders = {
    loadPerson: new DataLoader(async (ids: number[]) => {
      const people = await this.findPeopleByIds(ids);
      return ids.map(id => people.find(person => person.id === id));
    })
  };

  constructor(private db) {}

  private async findPeopleByIds(ids: number[]) {
    console.log(`[Person] Retrieving people with IDs: ${ids}`);
    return this.db.Person.findMany({ where: { id: { in: ids } } });
  }

  async getPerson(id: number) {
    return this.loaders.loadPerson.load(id);
  }
}
----

[NOTE.speaker]
====
Ce `DataLoader` regroupe les identifiants (IDs) demandés en une seule requête `findPeopleByIds`, ce qui réduit les appels individuels. `loadPerson` utilise ensuite cette requête pour récupérer et retourner les données, optimisant ainsi l’accès à la base de données.
====

== Étape 3 : Utilisation de DataLoader dans les résolveurs

Modifions les résolveurs pour utiliser `getPerson` de `PersonDataSource`, en tirant parti de DataLoader pour regrouper les requêtes.

1. Dans `src/resolvers/Query.ts`, configurez les résolveurs pour appeler `getPerson` via `dataSources`.

[source,typescript]
----
// src/resolvers/Query.ts

export default {
  Query: {
    person: (_, { id }, { dataSources }) => dataSources.personDataSource.getPerson(id),
    people: (_, __, { dataSources }) => dataSources.personDataSource.getAll(),
  },
};
----

[NOTE.speaker]
====
En utilisant `getPerson` avec DataLoader, les requêtes pour des personnes multiples sont regroupées et mises en cache. Cela améliore considérablement les performances lorsque des données imbriquées sont récupérées dans GraphQL.
====

== Étape 4 : Analyse de l'optimisation grâce au regroupement des requêtes

Nous allons tester une requête pour observer l'effet du regroupement. Exécutez la requête suivante pour récupérer des données imbriquées :

[source,graphql]

    name

      name

====
La requête `people` est exécutée avec un minimum de requêtes, car `DataLoader` regroupe les appels et utilise le cache interne pour éviter les appels redondants.

== Étape 5 : Utilisation avancée de DataLoader pour des requêtes complexes

Pour des cas plus avancés, nous pouvons configurer plusieurs loaders pour gérer différents types de requêtes (par exemple, chargement unique, multiple, et relations imbriquées).

### Exemple de configuration avancée dans `PrismaDataSource`

1. Modifiez `PrismaDataSource` pour ajouter des loaders pour des appels multiples ou pour des relations imbriquées.

[source,typescript]
----
// src/datasources/PrismaDataSource.ts

import DataLoader from 'dataloader';

class PrismaDataSource {
  private loaders = {
    loadOne: new DataLoader(async (ids: number[]) => {
      const results = await this.findMany(ids);
      return ids.map(id => results.find(item => item.id === id));
    }),
    loadRelated: new DataLoader(async (params: any[]) => {
      const results = await Promise.all(params.map(this.findRelated));
      return results;
    }, { cacheKeyFn: JSON.stringify })
  };

  constructor(private db) {}

  async getOne(id: number) {
    return this.loaders.loadOne.load(id);
  }

  async getRelated(params) {
    return this.loaders.loadRelated.load(params);
  }
}
----

[NOTE.speaker]
====
La méthode `loadOne` regroupe les requêtes par identifiant, tandis que `loadRelated` utilise `cacheKeyFn` pour convertir les paramètres en chaînes de caractères JSON. Cela permet de réutiliser des requêtes similaires et de réduire les appels vers la base de données.
====

== Étape 6 : Limitations et bonnes pratiques du regroupement et de la mise en cache

### Limitations de DataLoader

* **Cache local** : DataLoader utilise un cache en mémoire, donc les données sont perdues en cas de redémarrage du serveur.
* **Pas de persistance entre requêtes** : le cache de DataLoader n'est valable que pour une requête GraphQL unique.
* **Gestion des erreurs** : si une erreur survient lors du regroupement, tous les chargements peuvent échouer.

### Bonnes pratiques

* **Limiter l'usage de DataLoader aux requêtes intensives en base de données**.
* **Utiliser un cache persistant** (comme Redis) pour une mise en cache au-delà de la durée de vie d’une requête unique.
* **Désactiver le cache pour les données fréquemment mises à jour** pour éviter la livraison de données obsolètes.

[NOTE.speaker]
====
DataLoader est très utile pour optimiser les performances des API, mais il est important de gérer son cache avec prudence pour éviter les incohérences de données.
====
