== Introduction aux sources de données

Une source de données est une classe qui encapsule la logique de récupération des données, souvent depuis une base de données ou une API. Dans le cadre d’Apollo Server, les sources de données permettent de centraliser les appels aux données et d’optimiser les performances grâce à des techniques comme le batching et le caching.

**Avantages d'une source de données dédiée :**
* **Centralisation** : centraliser l'accès aux données pour une meilleure lisibilité et maintenance.
* **Optimisation** : optimiser les appels en réduisant les duplications grâce au batching et à la mise en cache.
* **Réutilisabilité** : faciliter la réutilisation de la logique de récupération de données dans différentes parties de l'API.

[NOTE.speaker]
====
Les sources de données dans Apollo Server permettent de gérer de manière efficace les interactions avec une base de données ou des services externes, en regroupant les requêtes et en minimisant les appels redondants.
====

== Étape 1 : Création d'une classe de base pour les sources de données

Pour structurer le code, nous allons créer une classe de base `BaseDataSource` qui contiendra les méthodes communes à toutes les sources de données, telles que `getOne` et `getAll`.

1 Dans le dossier `src/datasources`, créez un fichier `BaseDataSource.ts`.

[source,bash]
----
mkdir -p src/datasources
touch src/datasources/BaseDataSource.ts
----

2 Implémentez la classe `BaseDataSource` avec des méthodes génériques pour la récupération des données.

[source,typescript]
----
// src/datasources/BaseDataSource.ts

export class BaseDataSource {
  constructor(protected db: any, protected entityName: string) {}

  async getOne(id: number) {
    console.log(`[${this.entityName}] Retrieving the instance with identifier:`, id);
    return this.db[this.entityName].findUnique({ where: { id } });
  }

  async getAll() {
    console.log(`[${this.entityName}] Retrieving all instances.`);
    return this.db[this.entityName].findMany();
  }
}
----

[NOTE.speaker]
====
Cette classe de base fournit deux méthodes : `getOne` pour récupérer une instance unique par son identifiant, et `getAll` pour obtenir toutes les instances d’une entité. Ces méthodes peuvent être étendues par des classes spécifiques pour différentes entités, ce qui centralise et optimise le code.
====

== Étape 2 : Création d'une source de données pour une entité (ex : Person)

Maintenant que nous avons une classe de base, nous allons créer une source de données pour l’entité `Person`. Cette classe `PersonDataSource` héritera de `BaseDataSource` et permettra d’interagir spécifiquement avec les données de type `Person`.

1 Créez un fichier `PersonDataSource.ts` dans `src/datasources`.

[source,bash]
----
touch src/datasources/PersonDataSource.ts
----

2 Implémentez la classe `PersonDataSource` en utilisant `BaseDataSource` comme classe parente.

[source,typescript]
----
// src/datasources/PersonDataSource.ts

import { BaseDataSource } from './BaseDataSource';

export class PersonDataSource extends BaseDataSource {
  constructor(db) {
    super(db, 'Person');
  }
}
----

[NOTE.speaker]
====
La classe `PersonDataSource` hérite des méthodes `getOne` et `getAll` de `BaseDataSource`, ce qui permet de récupérer les données de l’entité `Person` sans répéter la logique de requêtes.
====

== Étape 3 : Utilisation de la source de données dans Apollo Server

Pour que la source de données soit accessible aux résolveurs, il est nécessaire de l'instancier dans le contexte d’Apollo Server.

1. Dans `src/index.ts`, ajoutez une instance de `PersonDataSource` dans le contexte.

[source,typescript]
----
// src/index.ts

import { ApolloServer } from 'apollo-server';
import { PersonDataSource } from './datasources/PersonDataSource';
import db from './db';

const server = new ApolloServer({
  typeDefs,
  resolvers,
  context: () => ({
    dataSources: {
      personDataSource: new PersonDataSource(db),
    },
  }),
});

server.listen().then(({ url }) => {
  console.log(`🚀 Server ready at ${url}`);
});
----

[NOTE.speaker]
====
En ajoutant `personDataSource` au contexte, les résolveurs peuvent maintenant accéder aux méthodes `getOne` et `getAll` pour interagir avec les données `Person`.
====

== Étape 4 : Utilisation des méthodes `getOne` et `getAll` dans les résolveurs

Nous allons maintenant utiliser `getOne` et `getAll` dans les résolveurs pour récupérer les données depuis la source de données `PersonDataSource`.

1. Dans `src/resolvers/Query.ts`, configurez les résolveurs `person` et `people` pour utiliser `getOne` et `getAll`.

[source,typescript]
----
// src/resolvers/Query.ts

export default {
  Query: {
    person: (_, { id }, { dataSources }) => dataSources.personDataSource.getOne(id),
    people: (_, __, { dataSources }) => dataSources.personDataSource.getAll(),
  },
};
----

[NOTE.speaker]
====
Les résolveurs `person` et `people` utilisent maintenant les méthodes `getOne` et `getAll` de `PersonDataSource`, ce qui garantit que les données sont récupérées de manière centralisée et optimisée.
====

== Étape 5 : Optimisation des requêtes pour les données imbriquées

Dans certains cas, des données imbriquées nécessitent plusieurs requêtes pour récupérer les relations. Cela peut entraîner des appels redondants et ralentir les performances. Pour optimiser, nous utiliserons des techniques de mise en cache et de batching (ex. : avec DataLoader) dans les sections suivantes, mais voici déjà une illustration du besoin d’optimisation.

=== Exemple de requête de données imbriquées

Imaginons une requête qui récupère une personne et les données imbriquées de son partenaire, ainsi que le partenaire du partenaire :

[source,graphql]
----
query Query {
  people {
    name
    partner {
      name
      partner {
        name
      }
    }
  }
}
----

**Exemple de réponse :**

[source,json]
----
{
  "data": {
    "people": [
      {
        "name": "John Doe",
        "partner": {
          "name": "Jane Doe",
          "partner": {
            "name": "John Doe"
          }
        }
      }
    ]
  }
}
----

[NOTE.speaker]
====
Ce type de requête peut générer des appels multiples pour chaque niveau de relation imbriquée, entraînant des duplications. Nous verrons comment optimiser cela en utilisant le batching et le caching dans un module ultérieur.
====
