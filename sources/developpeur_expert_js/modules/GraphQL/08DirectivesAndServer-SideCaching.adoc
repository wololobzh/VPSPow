== Introduction aux directives et au caching côté serveur

Les directives sont des annotations de schéma qui permettent d’ajouter une configuration supplémentaire à des parties du schéma ou à des opérations GraphQL. L’une des directives les plus utiles pour améliorer les performances est `@cacheControl`, qui permet de définir la durée de mise en cache d’un type ou d’un champ spécifique.

**Exemples de cas d’usage :**
* **@cacheControl** : permet de définir la durée pendant laquelle une requête ou un champ peut être mise en cache côté serveur.
* **Caching côté serveur** : améliore les performances en servant des données préenregistrées pour des requêtes identiques sans les recalculer.

[NOTE.speaker]
====
Les directives et le caching côté serveur sont des techniques avancées qui permettent de personnaliser et d'optimiser la gestion des données dans Apollo Server.
====

== Étape 1 : Activation de `@cacheControl`

La directive `@cacheControl` permet de contrôler la mise en cache des résultats des types ou des champs. Pour l’activer, il est nécessaire d’inclure la définition de la directive dans le schéma GraphQL.

1 Dans le dossier `src/schemas/directives`, créez un fichier `CacheControl.graphql`.

[source,bash]
----
mkdir -p src/schemas/directives
touch src/schemas/directives/CacheControl.graphql
----

2 Ajoutez la définition de `@cacheControl` dans ce fichier pour permettre le caching côté serveur.

[source,graphql]
----
enum CacheControlScope {
  PUBLIC
  PRIVATE
}

directive @cacheControl(
  maxAge: Int
  scope: CacheControlScope
  inheritMaxAge: Boolean
) on FIELD_DEFINITION | OBJECT | INTERFACE | UNION
----

[NOTE.speaker]
====
La directive `@cacheControl` accepte des options comme `maxAge` (en secondes), `scope` (PUBLIC ou PRIVATE), et `inheritMaxAge` pour contrôler la durée de vie en cache des données.
====

== Étape 2 : Utilisation de la directive `@cacheControl` dans le schéma

Une fois la directive configurée, elle peut être utilisée pour activer le caching au niveau des types ou des champs. Le caching est configuré soit directement dans le schéma, soit dans les résolveurs.

=== 2.1 Utiliser `@cacheControl` pour un type complet

Appliquons la directive à un type entier, par exemple `Restaurant`. La durée maximale (`maxAge`) de mise en cache sera définie à 240 secondes.

[source,graphql]
----
// src/schemas/types/Restaurant.graphql

type Restaurant @cacheControl(maxAge: 240) {
    id: Int!
    name: String!
    description: String!
    terrace: Boolean!
    address: String!
    city: City!
    manager: Manager!
    cuisines: [Cuisine!]
}
----

[NOTE.speaker]
====
Appliquer `@cacheControl` à un type entier active la mise en cache pour tous ses champs. Ici, les résultats du type `Restaurant` seront mis en cache pour 240 secondes.
====

=== 2.2 Utiliser `@cacheControl` pour des champs spécifiques

Il est aussi possible de configurer `@cacheControl` pour certains champs seulement, par exemple `city`, `manager` et `cuisines` du type `Restaurant`, pour une durée de 480 secondes.

[source,graphql]
----
type Restaurant @cacheControl(maxAge: 240) {
    id: Int!
    name: String!
    description: String!
    terrace: Boolean!
    address: String!
    city: City! @cacheControl(maxAge: 480)
    manager: Manager! @cacheControl(maxAge: 480)
    cuisines: [Cuisine!] @cacheControl(maxAge: 480)
}
----

[NOTE.speaker]
====
Dans ce cas, la durée de mise en cache des champs `city`, `manager`, et `cuisines` est de 480 secondes, tandis que le reste des champs du type `Restaurant` utilise la valeur par défaut de 240 secondes.
====

== Étape 3 : Mise en cache côté serveur dans les résolveurs

La mise en cache côté serveur peut aussi être configurée dans les résolveurs pour une gestion plus dynamique. En utilisant l’objet `info` (le quatrième argument des résolveurs), il est possible de définir un `cacheControl` spécifique par champ ou requête.

=== Exemple : Mise en cache pour le champ `manager` dans le résolveur

Dans `src/resolvers/Query.ts`, modifiez le résolveur `manager` pour définir un `cacheControl` de 480 secondes.

[source,typescript]
----
// src/resolvers/Query.ts

export default {
  Query: {
    managers: (_: any, { where }: any, { prisma }) => prisma.manager.findMany({ where }),
    manager: (_: any, { id }: { id: number }, { prisma }, { cacheControl }) => {
      cacheControl.setCacheHint({ maxAge: 480 });
      return prisma.manager.findUnique({
        where: { id }
      });
    },
  },
};
----

[NOTE.speaker]
====
En utilisant `cacheControl.setCacheHint({ maxAge: 480 })`, le résultat de `manager` sera mis en cache pour 480 secondes, sans avoir à spécifier cette valeur dans le schéma.
====

== Étape 4 : Avantages et limitations du caching côté serveur

### Avantages
* **Réduction des temps de réponse** : les requêtes répétitives peuvent être servies directement depuis le cache sans recalculer les résultats.
* **Économie de ressources** : moins de requêtes répétées vers les sources de données sous-jacentes, ce qui réduit la charge des API externes ou des bases de données.

### Limitations
* **Données obsolètes** : le cache peut servir des données qui ne sont plus à jour jusqu'à ce qu'elles expirent.
* **Invalidation complexe** : déterminer quand invalider le cache pour s'assurer que les données sont à jour peut être difficile.
* **Consommation de mémoire** : la mise en cache augmente l'utilisation de la mémoire sur le serveur, ce qui peut être problématique dans des environnements contraints en ressources.
* **Effet de "cache warming"** : après une invalidation, le cache peut prendre du temps à se remplir à nouveau, ce qui peut ralentir temporairement les performances.

[NOTE.speaker]
====
La mise en cache est une technique puissante mais qui comporte des défis, comme la gestion de la fraîcheur des données et le suivi de la consommation de mémoire. Des stratégies avancées peuvent être mises en place pour améliorer le contrôle de la durée de mise en cache, notamment l’utilisation de services comme Redis pour la persistance.
====

== Conclusion

// tag::conclusion[]
* Les directives permettent d’ajouter des configurations avancées dans les schémas GraphQL, comme `@cacheControl` pour la gestion du cache.
* La mise en cache côté serveur améliore les performances en évitant des requêtes répétitives et en conservant les résultats en mémoire.
* Bien que le caching présente des avantages importants, il nécessite des stratégies d'invalidation et de contrôle des données pour éviter des résultats obsolètes.
* Pour une mise en cache plus avancée et persistante, des solutions externes comme Redis peuvent être utilisées.
// end::conclusion[]
