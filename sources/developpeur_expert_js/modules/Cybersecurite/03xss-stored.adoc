== Introduction aux failles XSS stockées (Stored XSS)

Les failles XSS stockées (ou *Stored XSS*) permettent à un attaquant d’injecter un script malveillant qui est **stocké** dans la base de données de l'application. Contrairement aux failles XSS réfléchies, où le code malveillant est temporairement renvoyé dans la réponse, une faille XSS stockée reste dans l’application et s'exécute chaque fois qu'un utilisateur consulte la page concernée.

Les failles XSS stockées sont particulièrement dangereuses, car elles affectent tous les utilisateurs qui accèdent à la page infectée, rendant l’attaque durable.

[NOTE.speaker]
====
Les failles XSS stockées sont des vulnérabilités critiques, car le script malveillant reste dans la base de données et s'exécute chaque fois qu'un utilisateur affiche la page contenant le contenu infecté.
====

== Fonctionnement d'une attaque XSS stockée

Dans une attaque XSS stockée, un attaquant injecte du code malveillant dans un champ de saisie (ex. : commentaires, profil utilisateur) qui est ensuite sauvegardé dans la base de données. À chaque consultation de cette page, le script est chargé et exécuté dans le navigateur des utilisateurs.

**Étapes d’une attaque XSS stockée :**

1. **Injection du script** : L’attaquant soumet du code JavaScript malveillant dans un champ de saisie, comme un commentaire ou une biographie utilisateur.
2. **Sauvegarde du script** : Le script est stocké dans la base de données sans être correctement filtré.
3. **Exécution du script** : Chaque fois qu’un utilisateur consulte cette page, le script s’exécute dans son navigateur.

**Exemple d'injection de script dans un commentaire :**

```html
<!-- Contenu soumis par un utilisateur malveillant dans un champ de commentaire -->
<script>alert('Votre compte est en danger !');</script>
```

Si ce code est sauvegardé et affiché sans être échappé, il s'exécutera dans le navigateur de chaque utilisateur qui voit ce commentaire.

[NOTE.speaker]
====
Une attaque XSS stockée exploite un manque de validation des entrées, permettant au script malveillant d'être stocké dans la base de données et de s'exécuter dans les navigateurs des utilisateurs.
====

== Conséquences des attaques XSS stockées

Les failles XSS stockées peuvent avoir des conséquences importantes et variées sur les utilisateurs et les applications :

Vol de cookies de session et d’identifiants : Permet à un attaquant d'usurper l'identité de la victime.
Propagation de logiciels malveillants : Le script peut rediriger les utilisateurs vers des sites malveillants ou télécharger des logiciels malveillants.
Accès non autorisé aux comptes : Les attaquants peuvent obtenir un accès complet aux comptes d’utilisateurs en volant leurs sessions.
Détérioration de la réputation de l'application : Les attaques XSS peuvent entraîner une perte de confiance des utilisateurs et des impacts négatifs pour l'image de marque de l'application.


[NOTE.speaker]
====
Les conséquences des attaques XSS stockées peuvent être graves, notamment le vol de données, les accès non autorisés, et des impacts négatifs pour la réputation de l'application.
====

== Techniques de prévention des failles XSS stockées

Pour se protéger contre les failles XSS stockées, il est essentiel d'appliquer les bonnes pratiques de sécurité dans le traitement et l'affichage des données utilisateurs.

Échapper les caractères spéciaux : Assurez-vous d’échapper les caractères spéciaux (<, >, &, ', ") dans le contenu provenant des utilisateurs avant de l’afficher dans le HTML.
Valider et filtrer les entrées utilisateur : Filtrez et validez les données utilisateurs pour éviter l’injection de scripts.
Utiliser un Content Security Policy (CSP) : Configurez une politique de sécurité de contenu pour bloquer les scripts non autorisés.
Éviter d’autoriser le HTML dans les champs utilisateurs : Dans la mesure du possible, empêchez les utilisateurs de soumettre du HTML, surtout pour des champs comme les commentaires ou les descriptions de profil.
Utiliser des frameworks qui échappent les données par défaut : Des frameworks modernes comme React et Angular empêchent l'injection XSS en échappant les données par défaut.
Exemple de validation des entrées en JavaScript :

[source,javascript]
====
function sanitizeInput(input) { return input.replace(/[<>&'"]/g, function (c) { return ({ '<': '<', '>': '>', '&': '&', "'": ''', '"': '"' })[c]; }); }
====

[NOTE.speaker]
====
La protection contre les failles XSS stockées repose principalement sur l'échappement des caractères spéciaux, le filtrage des entrées, et l'application de Content Security Policy.
====

== Outils pour détecter les failles XSS stockées

Plusieurs outils permettent de détecter automatiquement les failles XSS stockées dans une application web :

OWASP ZAP (Zed Attack Proxy) : Cet outil open-source détecte les failles de sécurité, y compris les failles XSS.
Burp Suite : Un outil de sécurité avancé pour scanner, tester, et exploiter des failles comme les XSS stockées.
SonarQube : Analyse le code source pour identifier les vulnérabilités XSS dans les applications web.
XSSer : Un outil spécialisé dans le scan et l'exploitation des failles XSS, permettant de détecter les failles XSS stockées.
Ces outils permettent aux développeurs et aux testeurs de sécurité de détecter les failles XSS stockées en analysant le code et les comportements de l’application web.

[NOTE.speaker]
====
Les outils de scan, comme OWASP ZAP et Burp Suite, sont essentiels pour identifier et corriger les failles XSS stockées dans les applications, et minimiser les risques pour les utilisateurs.
====
