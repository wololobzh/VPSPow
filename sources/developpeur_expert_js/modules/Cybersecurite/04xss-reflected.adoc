== Introduction aux failles XSS réfléchies (Reflected XSS)

Les failles XSS réfléchies (ou *Reflected XSS*) sont des vulnérabilités qui permettent à un attaquant d'injecter du code malveillant dans une application web, de façon temporaire. Ce code est ensuite "réfléchi" dans la réponse envoyée par le serveur. Contrairement aux XSS stockées, le code injecté n'est pas sauvegardé dans la base de données, mais transmis dans les paramètres de la requête, ce qui signifie que le script malveillant ne s'exécute que si l'utilisateur interagit avec un lien ou un formulaire spécifique.

Les failles XSS réfléchies sont souvent exploitées via des liens malveillants contenant des paramètres non sécurisés ou mal filtrés.

[NOTE.speaker]
====
Les failles XSS réfléchies sont une menace courante, car elles exploitent les paramètres d'URL et autres entrées temporaires pour injecter des scripts malveillants dans une application web.
====

== Fonctionnement d'une attaque XSS réfléchie

Dans une attaque XSS réfléchie, un attaquant construit une URL contenant un script malveillant dans les paramètres. Si un utilisateur clique sur ce lien, l’application "réfléchit" le script dans la réponse, et le navigateur de l’utilisateur l'exécute.

**Étapes d’une attaque XSS réfléchie :**

1. **Construction du lien malveillant** : L'attaquant crée un lien incluant un code JavaScript dans les paramètres (par exemple dans une chaîne de recherche).
2. **Envoi du lien à la victime** : L’attaquant envoie ce lien par e-mail, message, ou autre moyen.
3. **Exécution du script** : Quand la victime clique sur le lien, le serveur inclut le script dans la réponse HTTP, l'exécutant dans le contexte de la session de l'utilisateur.

**Exemple d'URL malveillante :**

```html
https://exemple.com/search?q=<script>alert('XSS!')</script>
```


Si l'application intègre le paramètre `q` sans filtrer les caractères spéciaux, le script s'exécutera dans le navigateur de l’utilisateur.

[NOTE.speaker]
====
Le succès d'une attaque XSS réfléchie dépend souvent de l'interaction de l'utilisateur avec un lien contenant un script. L'attaque est réussie lorsque l'application renvoie ce script dans la réponse sans filtrage.
====

== Conséquences des attaques XSS réfléchies

Les impacts d’une faille XSS réfléchie peuvent être sévères, car ils exploitent la confiance de l'utilisateur envers le site :

* **Vol de cookies et d’informations de session** : Un script malveillant peut capturer les cookies de session, permettant à l’attaquant de se faire passer pour la victime.
* **Redirection vers des sites malveillants** : Le script peut rediriger les utilisateurs vers des sites de phishing ou malveillants.
* **Enregistreurs de frappe (Keyloggers)** : Un script peut enregistrer les saisies de l’utilisateur, permettant de voler des informations sensibles comme les mots de passe.
* **Faux formulaires** : Le script peut altérer le contenu de la page, par exemple en affichant de faux formulaires de connexion pour obtenir des informations d'authentification.

[NOTE.speaker]
====
Les attaques XSS réfléchies exploitent la confiance que les utilisateurs accordent à un site de confiance, rendant possible le vol de données sensibles ou la redirection vers des sites malveillants.
====

== Techniques de prévention des failles XSS réfléchies

Pour se protéger contre les failles XSS réfléchies, il est crucial d’appliquer de bonnes pratiques de sécurité lors de la gestion des données utilisateurs.

1. **Échapper les caractères spéciaux** : Évitez d’afficher des données d’utilisateurs directement dans le HTML sans échapper les caractères comme `<`, `>`, `&`, `'`, et `"`.
2. **Valider et assainir les entrées utilisateur** : Filtrer et valider les paramètres de requêtes et les données de formulaire pour empêcher l'injection de scripts.
3. **Utiliser Content Security Policy (CSP)** : Définir une politique CSP qui limite les sources autorisées de scripts, ce qui peut empêcher les scripts injectés de s’exécuter.
4. **Ne jamais afficher les paramètres de requête en HTML brut** : Ne pas injecter directement des paramètres de requête dans le contenu HTML sans filtrage.
5. **Utiliser des frameworks de rendu sécurisé** : Les frameworks modernes comme React et Angular échappent automatiquement les entrées utilisateurs, réduisant ainsi les risques d’injections XSS.

**Exemple de filtrage en JavaScript pour échapper les caractères spéciaux :**

[source,javascript]
----
function sanitizeInput(input) {
  return input.replace(/[<>&'"]/g, function (c) {
    return ({
      '<': '&lt;',
      '>': '&gt;',
      '&': '&amp;',
      "'": '&#39;',
      '"': '&quot;'
    })[c];
  });
}
----

[NOTE.speaker]
====
La meilleure façon de se protéger des XSS réfléchies est de s'assurer que les entrées utilisateur sont filtrées et échappées correctement, et de définir des politiques de sécurité de contenu strictes.
====

== Outils pour détecter les failles XSS réfléchies

Voici quelques outils pour tester les failles XSS réfléchies dans une application web :

1. **OWASP ZAP (Zed Attack Proxy)** : Outil open-source pour scanner les applications web et détecter les failles XSS, notamment les XSS réfléchies.
2. **Burp Suite** : Fournit des fonctionnalités avancées pour tester et exploiter les failles XSS dans les applications.
3. **XSSer** : Outil spécialisé dans la détection et l’exploitation des failles XSS, permettant de simuler des attaques XSS réfléchies.

Ces outils permettent aux développeurs et testeurs de sécurité de détecter les failles XSS réfléchies et de s'assurer que les données utilisateurs sont bien sécurisées.

[NOTE.speaker]
====
Les outils de scan comme OWASP ZAP et Burp Suite sont essentiels pour détecter les failles XSS réfléchies, car ils permettent de simuler des attaques et de vérifier si les paramètres sont correctement filtrés.
====

== Conclusion

// tag::conclusion[]
* Les failles XSS réfléchies exploitent des paramètres non sécurisés dans une application pour injecter et exécuter du code malveillant.
* Les conséquences incluent le vol de cookies de session, la redirection vers des sites malveillants et le détournement des actions de l’utilisateur.
* La prévention repose sur l’échappement des caractères spéciaux, la validation des entrées, et l’utilisation de Content Security Policy (CSP).
* Des outils comme OWASP ZAP et Burp Suite sont essentiels pour détecter et corriger les failles XSS réfléchies dans les applications.
