== Introduction

Il existe plusieurs stratégies de déploiement pour introduire de nouvelles versions de logiciels en production. Par exemple :

* Blue-Green
* Canary
* Rolling
* Shadow

[NOTE.speaker]
--
Les stratégies de déploiement sont cruciales pour garantir que les nouvelles versions de votre logiciel sont introduites en douceur, avec un minimum de risques. Elles sont particulièrement importantes dans les environnements de production où le temps d'arrêt peut être coûteux.
--

== Concepts clés

=== Déploiement Blue-Green

* **Avantages** : Permet des déploiements avec zéro temps d'arrêt, rollback facile en cas de problème
* **Cas d'utilisation** : Idéal pour les applications critiques nécessitant une haute disponibilité
* **Inconvénients** : Nécessite une double infrastructure, augmentant les coûts

[NOTE.speaker]
--
Le déploiement Blue-Green implique l'utilisation de deux environnements identiques, Blue et Green. Vous déployez la nouvelle version sur l'environnement inactif, puis basculez le trafic une fois prêt. Cela permet un retour en arrière rapide en cas de problème.
--

=== Déploiement Canary

* **Avantages** : Test progressif et contrôlé des nouvelles fonctionnalités, réduction des risques
* **Cas d'utilisation** : Utile pour valider l'impact des nouvelles fonctionnalités sur un sous-ensemble d'utilisateurs
* **Inconvénients** : Complexité accrue de la surveillance et de la gestion des versions

[NOTE.speaker]
--
Le déploiement Canary consiste à introduire la nouvelle version à un petit pourcentage d'utilisateurs, puis d'augmenter progressivement l'ampleur si tout se passe bien. Cela permet de minimiser les risques en détectant les problèmes potentiels tôt.
--

=== Déploiement Rolling

* **Avantages** : Déploiement progressif sans nécessiter une double infrastructure
* **Cas d'utilisation** : Utile pour les applications nécessitant une disponibilité continue
* **Inconvénients** : Risque de régression si les instances ne sont pas identiques

[NOTE.speaker]
--
Le déploiement Rolling remplace progressivement les instances de l'ancienne version par la nouvelle, une à une. Cela permet de minimiser l'impact sur les utilisateurs finaux tout en garantissant une disponibilité continue.
--

=== Déploiement Shadow

* **Avantages** : Test en parallèle des requêtes réelles sans impact sur les utilisateurs finaux
* **Cas d'utilisation** : Utile pour valider les performances et la compatibilité de la nouvelle version
* **Inconvénients** : Nécessite une configuration supplémentaire pour synchroniser les données

[NOTE.speaker]
--
Le déploiement Shadow consiste à rediriger une partie du trafic vers la nouvelle version sans affecter les utilisateurs finaux. Cela permet de tester en temps réel les performances et la compatibilité sans risque.
--

=== Autres stratégies de déploiement

* **A/B Testing** : Comparaison de deux versions pour évaluer les performances
* **Feature Toggles** : Activation/désactivation de fonctionnalités à la volée
* **Ring Deployment** : Déploiement progressif en cercles concentriques

== Avantages et Inconvénients

Il est important de choisir la bonne stratégie de déploiement en fonction de vos besoins spécifiques. 

* si la disponibilité est cruciale, Blue-Green peut être la meilleure option
* Pour des tests itératifs, Canary peut être plus approprié

== Bonnes pratiques

* Choisir la bonne stratégie selon le contexte
* Surveillance et rollback

[NOTE.speaker]
--
Choisir la bonne stratégie dépend de facteurs tels que la tolérance aux risques, la complexité de l'application, et les ressources disponibles. Assurez-vous d'avoir des mécanismes de surveillance en place pour détecter les problèmes rapidement, et des plans de rollback clairs.
--

== Exemple CI/CD Blue-Green


```yaml
name: Deploy NestJS Backend with Blue-Green Strategy

on:
  push:
    branches:
      - main

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v3

      - name: Set up Node.js
        uses: actions/setup-node@v3
        with:
          node-version: '18'

      - name: Install dependencies
        run: npm install

      - name: Build the project
        run: npm run build

      - name: Archive build
        run: zip -r build.zip dist

      - name: Upload build artifact
        uses: actions/upload-artifact@v3
        with:
          name: build
          path: build.zip

  deploy:
    runs-on: ubuntu-latest
    needs: build

    steps:
      - name: Download build artifact
        uses: actions/download-artifact@v3
        with:
          name: build

      - name: Extract build
        run: unzip build.zip

      - name: Set up Docker
        uses: docker/setup-buildx-action@v2

      - name: Log in to Docker Hub
        uses: docker/login-action@v2
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      - name: Determine active environment
        id: active-env
        run: |
          if kubectl get svc nestjs-service --namespace=prod-env -o jsonpath='{.spec.selector.color}' | grep -q 'blue'; then
            echo "active_env=blue" >> $GITHUB_ENV
            echo "inactive_env=green" >> $GITHUB_ENV
          else
            echo "active_env=green" >> $GITHUB_ENV
            echo "inactive_env=blue" >> $GITHUB_ENV

      - name: Build and push Docker image for inactive environment
        run: |
          docker build -t ${{ secrets.DOCKER_USERNAME }}/nestjs-backend:${{ env.inactive_env }} .
          docker push ${{ secrets.DOCKER_USERNAME }}/nestjs-backend:${{ env.inactive_env }}

      - name: Deploy to inactive environment
        run: |
          kubectl set image deployment/nestjs-backend backend-container=${{ secrets.DOCKER_USERNAME }}/nestjs-backend:${{ env.inactive_env }} --namespace=${{ env.inactive_env }}-env

      - name: Health check on inactive environment
        run: |
          curl -f http://${{ env.inactive_env }}-env.example.com/health || exit 1

      - name: Switch traffic to inactive environment
        run: |
          kubectl apply -f ${env.inactive_env}-ingress.yaml

      - name: Cleanup old active environment
        run: |
          kubectl delete deployment nestjs-backend --namespace=${{ env.active_env }}-env || true
```

[NOTE.speaker]
--
Ce pipeline utilise deux jobs : 

* un pour la construction de l'application NestJS 
* un pour le déploiement avec une stratégie blue-green. 

Les secrets GitHub sont utilisés pour sécuriser les informations de connexion à Docker Hub. La logique de basculement et de nettoyage est réalisée avec des commandes kubectl pour gérer le routage et la suppression des anciens déploiements.

Pour rendre la sélection de la plateforme (blue ou green) dynamique, une logique de détection automatique de l'environnement actif est utilisée. Cela permet de basculer automatiquement entre les environnements
--
